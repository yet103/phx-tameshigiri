## 0. 背景と決定

いまは二巡目の形（技 1〜3）を入れる場所が「一巡目を終了した後の二巡目の行」しかない。一巡目を終了した瞬間に一巡目の形を写して二巡目の行を作り、運営が「二巡目の形登録」の区画で自己申告のあった選手だけ直す（2026-09-22）。大会の前に申請を受けていても、当日の一巡目終了と二巡目開始の間（会場が待っている時間）に打ち込むしかない。

また PC 運営では、形登録の区画で直し終えたあと「試合進行へ →」で別の区画に移り、工程表の下の「二巡目を開始 ▶」を押す必要があり、どこで次へ進むのかが分かりにくい。

ユーザーの決定（2026-10-03）:

1. **二巡目の形も、大会の前に申請を受けて最初から登録しておく。** 一巡目を終了したときは、登録済みの二巡目の形で二巡目の行を作る。
2. **「二巡目の形登録」の区画から試合進行を再開する導線を直す。**

本書で決めること（推奨。11 章の決定待ちで最終確認する）:

| 論点 | 推奨 |
|---|---|
| データ | 一巡目の行に `r2tech1` `r2tech2` `r2tech3`。**3 つとも空 = 一巡目と同じ形**（キーごと持たない） |
| 空欄の判定 | **3 つとも空なら一巡目の形を写す。1 つでも入っていればその行の指定どおり（空欄は空のまま）**（2.2） |
| 形登録の段階（`round1_done`） | 当日の変更と最終確認の場として残す。二巡目の行の技を直すと一巡目の行の `r2tech` に**書き戻す**（2.4） |
| 一巡目の行の `r2tech` の変更 | 二巡目の行がまだ無ければ自由。あれば二巡目の行へ**書き写す**（採点済みなら 409 `scored`、force で越える）（2.4） |
| 試合開始の確認 | 二巡目の形の申請の人数を**情報として**出す（警告にしない）。申請された形の誤り（表に無い技・同じ形・レンタル）は**止める**（5 章） |
| 二巡目の開始 | 二巡目の行の技の誤り（表に無い技・同じ形・レンタル）を**止める**（5 章） |
| CSV | 拡張形式を **20 列 → 23 列**（末尾に `二巡目 技 1〜3`）。旧 20 列も受ける。簡易形式も 10 列 → 13 列（3.6） |
| 導線 | **工程表（①一巡目 → ②形登録 → ③二巡目）を部品にして、形登録の区画の先頭にも出す**。遷移ボタンは引き続き工程表の中だけ（6.4） |

## 1. 用語

- **一巡目の行** … `order` の巡目が 1 の行（`EventStatus.roundOf(p) === 1`）。選手 1 人に 1 行。
- **二巡目の行** … 巡目が 2 の行。一巡目の終了でサーバーが作り、`sourcePlayerId` で一巡目の行を指す。
- **二巡目の形（申請）** … 一巡目の行が持つ `r2tech1〜3`。二巡目の行を作るときの初期値。
- **実際の二巡目の形** … 二巡目の行の `tech1〜3`。採点画面・配信ボードが使うのはこちらだけ。

## 2. データの形

### 2.1 新しい項目

一巡目の行に次の 3 つを持たせる（命名は既存の `tech1〜3` にそろえ、「二巡目の」を `r2` の接頭辞で表す）。

```
players[]（一巡目の行だけ）
  r2tech1: string   二巡目の技 1（trim 済み、50 字まで。技得点表の名前か、接尾辞なしの表示名）
  r2tech2: string
  r2tech3: string
```

- **3 つとも空ならキーごと持たない**（`note` と同じく「無い = 空」）。1 つでも入っていれば 3 つとも書く（空の枠は `''`）。
- **二巡目以降の行は持たない**。保存の経路（`sanitizePlayerForSave`・PATCH・POST）で二巡目の行に付いていたら落とす（PATCH・POST は 400。3.3・3.2）。
- **互換**: キーの無い行（この機能より前の大会・申請の無い選手）は「空 = 一巡目と同じ形」。移行の処理は要らない。
- **版（rev）は上げない**。`REV_FIELDS`（`server/index.js:363`）に足さない。一巡目の行の採点には関わらないので、`r2tech` を直しても一巡目を採点中の端末を衝突（409 `stale`）にしない。二巡目の行へ書き写したときは、写した先の行の `tech1〜3` が変わるので、そちらの rev は従来どおり +1 になる。
- 採点の鍵の PATCH（`authz.SCORER_PATCH_KEYS`）には足さない。採点端末が送れば従来どおり 403 `field`（運営の項目）。

### 2.2 二巡目の形の決め方（共通関数）

`status.js`（サーバーと画面で共有）に足す:

```js
EventStatus.R2_TECH_KEYS = ['r2tech1', 'r2tech2', 'r2tech3'];
// 申請があるか（3 つのうち 1 つでも空白以外が入っているか）
EventStatus.hasRound2Techs(p) -> boolean
// 二巡目の行に入れる形。申請が無ければ一巡目の tech1〜3、あれば r2tech1〜3 をそのまま（空の枠は ''）
EventStatus.round2TechsOf(p) -> [string, string, string]
```

**3 つとも空なら一巡目を写し、1 つでも入っていればその行の指定どおり（空欄は空）にする理由**:

1. 申請の書き方が単純になる。「二巡目も同じなら何も書かない、変えるなら 3 つ書く」。技ごとに空欄を一巡目で埋めると、`r2tech1` だけ書いた人の 2・3 本目が一巡目の 2・3 本目になり、**同じ形の回数制限に意図せず当たる**（例: 一巡目 `袈裟・逆袈裟・水平`、申請 `水平, '', ''` → 写すと `水平・逆袈裟・水平`）。
2. 二巡目を 2 本で行う申請（ヘルプ「事情があれば 2 つでも採点はできます」）を表せる。技ごとに埋める方式では `'', ''` と書いても一巡目で埋まってしまう。
3. 書き戻し（2.4）と往復（CSV・バンドル）で値が一意に決まる。

不便な点（1 本だけ変える人も 3 つ書く必要がある）は入力画面で補う: 申請が空の選手の二巡目の欄を開くと、**一巡目の形を下書きとして入れた状態**で始める（6.1・7.1）。1 本だけ選び直して保存すればよい。

### 2.3 正規化

`r2tech1〜3` を保存するとき（`r2tech` を送った PATCH・POST・bulk・CSV・バンドル・`POST /api/events`・大会のコピー・技得点表の改名）、**その行の `tech1〜3` と 3 つとも同じなら空として保存する**（キーを消す）。

- `tech1〜3` だけの PATCH では正規化しない（申請に触らない）。一巡目の形を一時的に申請と同じ形に直しただけで申請が黙って消え、形を戻しても復活しない、という食い違いを避けるため（レビュー指摘 2026-10-03）。このとき申請は一巡目の形と同じ値のまま残るが、`round2TechsOf` は同じ形を返すので二巡目の形は変わらない。

- 「一巡目と同じ形」を表す値を 1 つにそろえる（CSV で一巡目の形をそのまま書いた申請も「申請なし」と同じに扱う）。2.5 の「一巡目の形を直すと二巡目の行も付いていく」がその選手にも効く。
- 比べるのは trim 後の文字列（性別の接尾辞の有無も区別する。`破図味` と `破図味(男)` は別の値として比べる）。

### 2.4 二巡目の行との同期

二巡目の行ができたあと（`round1_done` 以降。正確には「`sourcePlayerId` でその一巡目の行を指す二巡目の行があるとき」）、申請（一巡目の行の `r2tech`）と実際の形（二巡目の行の `tech1〜3`）は次の規則で一致させる。状態ではなく**二巡目の行があるかどうか**で決める（一巡目に戻した `round1` でも二巡目の行は残っているため）。

| 操作 | 書き換える先 |
|---|---|
| 一巡目の行の `r2tech` を直す（PATCH に `r2tech1〜3` のどれかがある） | 紐づく二巡目の行の `tech1〜3` を `round2TechsOf(一巡目の行)` に書き写す（rev +1）。写す先が採点済み（`isScored`）で値が変わるなら、`force` が無ければ **409 `scored`**（3.3） |
| 二巡目の行の `tech1〜3` を直す（形登録の区画・PC の選手登録・スマホの編集シート） | 元の一巡目の行の `r2tech` に**書き戻す**。新しい形が一巡目の行の `tech1〜3` と 3 つとも同じなら `r2tech` を空に、違えばその 3 つを入れる（一巡目の行の rev は上げない） |
| 「一巡目と同じ形に戻す」（形登録・スマホの進行タブ） | 上の 2 行目の特別な場合。二巡目の行が一巡目と同じ形になり、申請は空に戻る |

**書き戻す理由**: 申請と実際がずれると、(a) 一巡目に戻して終了し直したときの作り直し（`reorderRound2`）や差分追加で、どちらを使うかの判断が要る、(b) CSV・バンドルで書き出した申請の列が当日の変更を反映しない、(c) PC の選手登録の表で「二巡目の形」の列と二巡目の行の技が食い違って見える。形登録で直した形は、そのまま「その選手の二巡目の形」として残るのが自然。

**割り切り**: 二巡目の行の技を 3 つとも空にすると、書き戻した申請も空 = 「一巡目と同じ」になる（空と「一巡目と同じ」を区別できない）。3 つとも空の行は採点できない（工程表の「技 未入力」に数え、二巡目の開始の確認で知らせる）ので実害は小さい。ヘルプに書く。

### 2.5 一巡目の形を直したとき（申請が空の選手）

申請が空（= 一巡目と同じ）の選手の一巡目の行の `tech1〜3` を、二巡目の行ができたあとで直したとき、**紐づく二巡目の行が未採点で、その技が直す前の一巡目の形と 3 つとも同じなら、二巡目の行も新しい形に合わせる**（rev +1）。

- 「空 = 一巡目と同じ」を、二巡目の行ができたあとも守るため（受付の打ち間違いを一巡目終了の後に直した、など）。
- 二巡目の行が採点済み、または形登録で既に別の形に直してある（直す前の一巡目の形と違う）なら触らない。
- 今は付いていかない（一巡目の行を直しても二巡目の行はそのまま）ので、挙動の変更になる。11 章 D3。

2. 採点の PATCH の版と状態（変更なし）。
3. 409 `linked`（変更なし）。
4. **409 `scored`** に追加: この PATCH で一巡目の行を書き換えた後の状態から、紐づく二巡目の行（`linkedRows`）ごとに書き写すかどうかを決める（下の 3.3.1）。申請（`r2tech`）を送っていて、書き写す行が採点済みで、`force` が無ければ:

5. 409 `bib`（変更なし）。

- `r2tech` を送られたら 3 つをそろえて置き換える（送られていない枠は今の値。そのあと 2.3 の正規化。3 つとも空ならキーを消す）。`tech1〜3` だけの PATCH では正規化しない（申請に触らない。2.3）。
- `body.round` で行が一巡目以外に移ったら `r2tech` を消す。

#### 3.3.1 一巡目の行 → 二巡目の行への書き写し

一巡目の行の PATCH で、`before`（書き換え前の複製）と `player`（書き換え後）から:

```
oldTarget = round2TechsOf(before)
newTarget = round2TechsOf(player)
r2Sent    = 本文に r2tech1〜3 のどれかがある
linkedRows.forEach(L => {
  if (newTarget と oldTarget が同じ) return                     // 二巡目の形は変わっていない
  if (L の tech1〜3 が newTarget と同じ) return                  // もう同じ形
  if (r2Sent) {                                                  // 申請を直した → 書き写す（採点済みは 409 / force）
    L.tech1〜3 = newTarget, rev +1
  } else if (L が未採点 && L の tech1〜3 が oldTarget と 3 つとも同じ) {   // 一巡目に付いていく行（2.5）
    L.tech1〜3 = newTarget, rev +1
  }
  // それ以外（申請は変えていない・L は採点済みか、形登録で別の形に直してある）: 触らない
})
```

- 4 の 409 `scored` は、`r2Sent` で書き写す行が採点済みのときだけ出す（2.5 の「付いていく」は採点済みの L に適用しないので、そちらでは断らない）。
- 一巡目の行自身の `tech1〜3` を変えて、一巡目の行が採点済みなら、従来どおりの 409 `scored`（`linked` なし）。
- 決戦の行（`finalist`）も同じ扱い（二巡目の行であることは変わらない）。

#### 3.3.2 二巡目の行 → 一巡目の行への書き戻し

二巡目の行の PATCH で `tech1〜3` が実際に変わり、`sourcePlayerId` が今ある一巡目の行 `S` を指していれば、書き換えのあとで `S.r2tech` を 2.4 の規則で書き戻す（`S` の rev は上げない）。409 `scored` の判定は従来どおり（二巡目の行自身が採点済みなら force が要る）。

#### 3.3.3 応答

`{ success: true, player }` に、書き換えた相手の行を足す（画面がその行だけ差し替えるため。PC の選手登録の表は描き直さない方針）:

- 一巡目の行の PATCH で二巡目の行を書き換えたら `linked: [playerWithRev(L), …]`
- 二巡目の行の PATCH で一巡目の行を書き戻したら `source: playerWithRev(S)`

### 3.4 二巡目の行を作る（`buildRound2Row` / `generateRound2` / `reorderRound2`）

- `buildRound2Row`（`index.js:3774`）: `tech1〜3` を `EventStatus.round2TechsOf(p)` で決める（申請が無ければ従来どおり一巡目の複製）。新しく作る行はすべてここを通る（通常の生成・差分追加・作り直しで対応する既存行が無い選手）。
- `reorderRound2`（`index.js:3905`。誰も採点していない二巡目を作り直す）: 既存の行（`old`）の `tech1〜3` を保つのは**変えない**。2.4 の同期で `old` の技はいつも申請と一致しているため（形登録で直した形が作り直しで消えない、という今の約束も守れる）。
- 生成は一巡目の行を書き換えない（変更なし）。
- 応答の `round2Info` に `fromRequest`（申請の形で作った行の数）を足す。トーストに「（二巡目 20 名分作りました・申請の形 3 名）」のように出す（0 名なら書かない）。

### 3.5 技得点表の改名（`planTechniqueChange`。`index.js:3301`）

- 調べる枠を `['tech1', 'tech2', 'tech3', 'r2tech1', 'r2tech2', 'r2tech3']` にする。
  - 付け替え（`renames`）は `r2tech` も同じ規則で付け替える（接尾辞なしの表示名は接尾辞なしで）。
  - 消える技の数え方（`vanished` の `count` は行の数、`usages` は技ごとの行の数）は、`r2tech` で使っている行も数える（同じ行の `tech` と `r2tech` に同じ技があっても 1 行）。
- 付け替えた行の rev: `tech` が変わった行だけ +1（`r2tech` だけの付け替えでは上げない。2.1）。
- `DELETE /api/events/:id/techniques`（雛形に戻す）も `applyTechniqueChange` を通るので同じ。

### 3.6 CSV

#### 3.6.1 拡張形式（書き出し・往復）: 20 列 → 23 列

```
選手名,順番,技 1,技 2,技 3,得点,新人,女子,結果,補正点1,補正点2,補正点3,全体補正,備考,確定,ゼッケン,級位段位,レンタル,決戦,一巡目の行,二巡目 技 1,二巡目 技 2,二巡目 技 3
```

- 新しい 3 列は**末尾（21〜23 列目）**に足す。既存の列の位置を変えない（取り込みの添字・既存のテスト・利用者の Excel の列がずれない）。
- 値: 一巡目の行は `r2tech1〜3`（申請が無ければ空）。二巡目の行は常に空（二巡目の行の形は 3〜5 列目の `技 1〜3`）。
- `CSV_EXPORT_HEADER` を 23 列にし、`CSV_ROUNDTRIP` の後ろに `CSV_R2TECH = ['二巡目 技 1', '二巡目 技 2', '二巡目 技 3']` を足す。

#### 3.6.2 取り込み（`POST /api/events/:id/import`）

- 見出しの正規化（`normalizeCsvHeaderCell`）: 空白を落とした `二巡目技1` と `二巡目技①` を同じものとして扱う（今の `技①` → `技1` と同じ読み替えを `^二巡目技([①②③])$` にも掛ける）。
- 従来形式の候補に **23 列**（`roundtrip: true, r2: true`）を足し、**20 列は残す**（`roundtrip: true, r2: false`。旧版で書き出したファイル）。
- 23 列のとき: 一巡目の行は 21〜23 列目を `r2tech1〜3` として読む（`sanitizePlayerForSave` が洗い、二巡目の行の値は捨てる）。20 列以前の形式では `r2tech` は空。
- **置換・追記の判定（`round2_format`）**: 「往復できる形式」を `fmt.roundtrip`（20 列か 23 列）のまま判定する。二巡目がある大会へ 20 列で置き換えると申請は空になるが、二巡目の行の形（実際の形）は 3〜5 列目で往復するので、決戦とつながりを守るという `round2_format` の目的は満たす。
- `round2_format` の文言: 「二巡目がある大会には、CSV エクスポートで書き出した形のファイル（23 列。以前の 20 列も可）だけ取り込めます（置換・追記とも）」。
- `expectedCount`・文字化け・採点済みの置換の検査は変えない。

#### 3.6.3 簡易形式: 10 列 → 13 列

```
名前,コート,性別,技①,技②,技③,新人,ゼッケン,級位段位,レンタル,二巡目技①,二巡目技②,二巡目技③
```

- 「先頭から 2 列以上」の規則はそのまま（`CSV_SIMPLE_COLS` を 13 にするだけ。10 列以下のファイルは今までどおり読める）。
- 11〜13 列目を `r2tech1〜3` として読む（一巡目の行として採番するので必ず有効）。
- 足す理由: 大会前の申請の一覧（受付の Excel）から取り込むのは主にこの形式。拡張形式（23 列）は得点や順番の列まであって、受付の名簿には向かない。
- 技名の検証はしない（今の簡易形式と同じ。試合開始の検査で止まる）。

### 3.7 バンドル（`GET /api/events/:id/bundle` / `POST /api/events/import`）

- `pickBundlePlayer`（`index.js:3470`）: 一巡目の行で申請があれば `r2tech1〜3` を出す（`note` と同じく「あるときだけ」）。
- 取り込みは `sanitizePlayerForSave` を通るので、追加の処理は要らない。
- `BUNDLE_VERSION` は 1 のまま（キーが増えるだけ。古いサーバーは知らないキーを落とす＝申請が空になるだけで壊れない）。

### 3.8 大会のコピー（`POST /api/events/:id/copy` の `withPlayers`）

一巡目の行の `tech1〜3` を写しているのと同じ扱いで、`r2tech1〜3` も写す（`index.js:1675` の複製に足す）。11 章 D10。

### 3.9 変えないところ

- 採点の鍵（`authz.SCORER_PATCH_KEYS`）: 足さない。`r2tech` を送れば 403 `field`。
- 順位・決戦・配信ボード・共有ページ・採点画面: 二巡目の行の `tech1〜3` だけを使うので変更なし。

2026-09-30 の決定（`desk-round2.js` 冒頭「段階の遷移ボタン（二巡目を開始 など）は試合進行の工程表の下にだけ置く」）の目的は、(a) 試合進行は進み具合を見る画面、形登録は形を直す画面と役割を分けること、(b) 段階を変えるボタンと確認の経路を 1 つにして、あちこちに「進む」ボタンを散らさないこと、だった。推奨案は:

- 決定の文言は「遷移ボタンは**工程表の中にだけ**置く。工程表は試合進行と、その段階の作業をする区画（形登録）の先頭に出す」に改める。
